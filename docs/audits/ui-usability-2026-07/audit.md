# Chrona UI 사용성 감사

## 감사 범위

- 대상: Chrona Desktop의 저장소 열기 이후 주요 작업 흐름
- 사용자 목표: 저장소 상태를 빠르게 파악하고, 소스 선택·스냅샷·파일 탐색·통계·무결성 확인으로 자연스럽게 이동하기
- 접근성 목표: 키보드와 좁은 화면에서도 핵심 작업에 빠르게 도달할 수 있는 구조
- 캡처 환경: 2026-07-07, Google Chrome + Playwright, 데스크톱 1440×960, 모바일 390×844
- 데이터: 실제 제품 컴포넌트에 현실적인 감사용 API 응답을 연결했으며 제품 코드는 변경하지 않음

## 강점

- 사이드바의 아이콘, 명칭, 현재 선택 상태가 일관되어 데스크톱 탐색은 쉽다.
- 저장소 열기 후 소스 화면으로 이동하고, 소스 선택 후 실행 버튼이 활성화되는 순서가 자연스럽다.
- 라이트/다크 모드에서 같은 정보 구조와 상태 색상을 유지한다.
- 통계 화면은 논리 용량, 중복 제거, 압축, 물리 저장량을 분리해 비교하기 쉽다.
- 상태는 색상만이 아니라 `Ready`, `Available`, `Healthy` 같은 텍스트도 함께 제공한다.
- 파일 탐색기는 검색과 세 가지 필터, 목록과 상세를 한 흐름으로 연결한다.

## UX 위험

### 구조 문제

1. 모든 장에서 장 제목, 네 개 상태 요약, 두 개 경로, 패널 제목이 반복된다. 1440×960에서 실제 패널 내용은 약 340px 이후에 시작한다.
2. `Repository open`은 상단 툴바, 요약, 경로, 사이드바 하단에 반복된다. 사용자가 새 정보를 찾는 대신 같은 상태를 계속 읽게 된다.
3. `Available`, `Ready`, `Waiting`, `Loaded`의 차이가 명확하지 않다. 특히 `Available`은 현재 상태인지 실행 가능 여부인지 해석이 갈린다.
4. `Chrona Phase 2`는 현재 개발 단계와 맞지 않아 제품 상태에 대한 신뢰를 떨어뜨린다.
5. 하단 세션 푸터는 작업이 없을 때도 데스크톱 높이 52px을 계속 점유한다.

### 작업 화면 문제

1. 홈은 계속 작업, 저장소 개요, 고정 항목, 최근 항목이 하나의 긴 패널에 들어 있어 우선순위가 약하다.
2. 스냅샷은 생성, 선택, 복원, 파일 목록, 비교가 한 세로 흐름에 있어 화면을 많이 내려야 한다.
3. 탐색기는 상단 공통 정보가 높이를 사용해 목록과 파일 상세가 동시에 충분히 보이지 않는다.
4. 파일을 선택해도 핵심 블록 맵과 버전 상세가 첫 화면에 들어오지 않는다.
5. 무결성 화면은 결과가 짧은데도 다른 화면과 동일한 큰 패널을 사용해 정보 밀도가 지나치게 낮다.

### 반응형 문제

1. 390×844에서 툴바 높이는 약 109px, 사이드바 높이는 544px이며 본문은 `y=652.75px`에서 시작한다.
2. 모바일 사용자는 홈을 선택한 뒤에도 전체 탐색 메뉴를 지나야 실제 홈 내용을 볼 수 있다.
3. 모바일 전체 문서 높이가 약 2,862px이며 고정된 앱 셸이 아니라 긴 웹 문서처럼 동작한다.

## 접근성 위험

- 테마 아이콘 버튼은 34×34px으로 일반적인 44×44px 터치 목표보다 작다.
- 모바일에서 본문 전에 탐색 버튼 8개가 배치되어 키보드와 스크린 리더 사용자의 핵심 콘텐츠 도달 비용이 크다.
- 연한 보조 텍스트와 비활성 버튼의 명암 대비는 별도 수치 검증이 필요하다.
- `Available`과 `Ready`처럼 의미가 가까운 상태가 반복되어 보조 기술 사용자에게도 상태 구분이 불명확할 수 있다.
- 스크린샷만으로 실제 포커스 표시, 탭 순서, 스크린 리더 알림, 확대 200% 동작은 확인할 수 없다.

## 개선 기회

1. 앱 셸을 고정 영역으로 다시 나눈다: 얇은 상단바, 접을 수 있는 사이드바, 독립 스크롤 본문, 필요할 때만 나타나는 작업 상태 바.
2. 장 공통 정보는 한 줄의 저장소 컨텍스트 바로 줄이고, 세부 경로는 필요한 장에서만 표시한다.
3. 사이드바는 현재 위치만 강조하고 `Available` 배지를 제거한다. 주의나 실패처럼 행동이 필요한 상태만 배지로 남긴다.
4. 모바일에서는 사이드바를 기본 접힘 상태의 드로어로 바꾸고 본문을 첫 화면에 배치한다.
5. 홈은 최근 작업과 저장소 핵심 수치만 유지한다. 상세 통계는 Statistics로 이동시킨다.
6. Explorer는 상단 필터를 고정하고 목록과 상세가 각각 독립 스크롤하는 작업 화면으로 만든다.
7. Snapshots는 목록/상세를 기본 구조로 두고 생성과 복원은 명확한 작업 영역 또는 대화상자로 분리한다.

## 권장 방향

기능과 데이터 흐름은 유지하고 **앱 셸과 정보 위계를 먼저 정리하는 단계적 개선**을 권장한다.

- 1차: 앱 셸, 사이드바, 스크롤, 공통 컨텍스트, 상태 문구, 모바일 탐색
- 2차: Home, Repository, Sources의 주요 작업 위계
- 3차: Snapshots, Explorer, Statistics, Integrity의 데이터 밀도와 독립 스크롤
- 4차: 키보드 포커스, 대비, 200% 확대, 390px/768px/1440px 회귀 검증

전체 화면을 한 번에 재작성하면 이미 동작하는 기능의 회귀 범위가 커진다. 공통 셸을 먼저 고정하고 장별 화면을 같은 규칙으로 옮기는 편이 현재 프로젝트 상태에 맞다.

## 증거 한계

- 감사용 데이터로 화면 상태를 재현했으므로 실제 대용량 저장소의 렌더링 성능은 측정하지 않았다.
- macOS Tauri 네이티브 창 장식, 파일 선택 대화상자, 운영체제별 폰트 차이는 캡처 범위에 포함하지 않았다.
- 접근성 적합성 판정이 아니라 스크린샷과 DOM 크기에서 확인되는 위험을 기록했다.
